# Supabase Edge Functions

Deno runtime, deployed with `supabase functions deploy <name>`. These run server-side with the service role via `Deno.env.get('SUPABASE_SERVICE_ROLE_KEY')`.

## Conventions

- **One function per subsystem, `action`-dispatched.** `game-service` handles every write to the games subsystem; new game operations become new cases in `switch (body.action)`. Grow this before spinning up a second function.
- **Authenticate the caller via their JWT** (`Authorization` header → anon-key client → `auth.getUser()`), then do all reads/writes with the service-role admin client. 401 if unauthenticated.
- **Writes bypass RLS** (service-role key), so mutated tables don't need client-writable policies. Keep select policies permissive enough for the app's realtime/read paths.
- **Background tasks via `EdgeRuntime.waitUntil(promise)`** — runs after the response returns; make the work idempotent in case the function runs twice.
- **Best-effort side writes must not fail the action.** On completion `commitActionWrite` summarizes the game into `game_results` (the Stats tab's source, since `game_states` is live-shaped and can't be rescored later); that write only logs on failure — the game is over, the caller is owed its 200, and `dev/backfill-game-results.ts` can rebuild any missing row.
- **`commitActionWrite` is the only place a game ends.** Its `opts` bag covers the two non-victory endings: `gameFields` merges extra columns (`forfeits`/`end_votes`), `byForfeit` stamps the results rows, and `canceled` sets `status = 'canceled'` and **skips the results write entirely** — a canceled game contributing nothing to stats is enforced by never writing the summary, not by filtering later. New endings belong here so the state → games → results ordering stays in one place.
- **`set_forfeit` / `set_end_vote` are idempotent setters.** Each takes `{ game_id, on }`; a re-send matching the stored array returns 200 without writing. Both resolve the caller's seat with `player_order.indexOf`, **not** `currentPlayerIndex` (which is null for the whole bonus-selection phase). Neither declaration has any mechanical effect; see the forfeiting section of `lib/catan/CLAUDE.md`.
- **`run_timeouts` is the one action with no user behind it.** The move-timeout sweep is driven by `pg_cron` and authorized by matching the bearer against `SUPABASE_SERVICE_ROLE_KEY`, so `serve` branches to it **before** `callerUserId`. Its auto actions re-enter the ordinary handlers through `dispatch` — the runner picks an arbitrary legal choice and re-implements no game rule, which is why the sweep lives in this function. See `.claude/specs/move-timeouts.md`.
- **`games.deadline_at` is maintained in `serve`, like `game_states.undo`.** After any successful action carrying a `game_id`, `refreshDeadline` re-reads the rows, drops the caller from `games.timed_out`, and re-stamps the deadline — one place rather than fifty handlers, inside `waitUntil`. `TIMEOUT_NEUTRAL_ACTIONS` (`honk`, `send_message`) are exempt, the same reason `lastActivityAt` ignores honks.
- **`dev-login` mints a session for any account** (backs admin "Act as" impersonation — see `lib/admin.ts`), so it has no caller to authenticate and runs `verify_jwt = false`. Because the target is a request parameter, its `DEV_LOGIN_KEY` header **is** a security boundary and must never ship in a bundle (read from local `.env`, which no EAS build populates; the function 500s if the secret is unset, so a project without it exposes nothing). The session is minted through a magic link (admin `generateLink` → client `verifyOtp`), **not** a password: setting a password revokes every existing session for the account (GoTrue), which would sign the real owner out. A phone-only account with no email gets a synthetic namespaced one.
- **`reviewer-login` is the other no-caller function** (the App Store reviewer bypass). It authorizes on an `x-reviewer-key` matched against `REVIEWER_KEY`, which the bundle ships in plaintext — that's friction, not a boundary, since the endpoint grants a session for one specific account by design. It signs in with a **fixed** `REVIEWER_PASSWORD` (rotating would revoke that account owner's other sessions). `dev/seed-reviewer-login.mjs` sets both halves.
- **Error shape:** `{ ok: false, error: string }` + an appropriate status. The client surfaces a generic message; the error strings are for logs.
- **CORS is required** for web callers: handle `OPTIONS` preflight and add `Access-Control-Allow-Origin` to every response.

## Notifications (`_notify`)

`sendNotifications` titles every push `'Settled'` and generates the body from the kind. Two opt-in escapes, both used by `chat_message`: `titleFrom: 'sender'` (title becomes the sender's username) and `bodyOverride` (arbitrary text, truncated to `MAX_BODY_CHARS`). A target with no `gate` always sends (honk, the forfeit/end-game kinds, the two move-timeout kinds — all rare and consequential enough to skip a preference toggle).

- **`NotificationKind` here is a twin of the union in `lib/notifications/links.ts`.** Adding a kind server-side without adding it there sends the tap to `default`, which returns `null` — the push arrives and tapping does nothing (exactly how `honk` shipped broken). A kind that names something must carry its id (`game_id`, or `request_id` for `game_invite`).
- **The app-icon badge is not a notification count** — it's the recipient's number of in-progress games waiting on them (`badgeCounts`, the server mirror of `isMyTurn`). It rides every kind, so any push corrects a badge that drifted while the app was closed, and a user with nothing waiting gets an explicit `0`. This works only because `sendNotifications` sits after its write has committed (inside `waitUntil`) — notifying before committing would badge the pre-action count.
- **`_shared/phase.ts` is the one server copy of "who is this game waiting on"**, shared by `game-service` (move timeouts) and `_notify` (the badge). Its `PendingPhase` is deliberately narrower than `game-service`'s `Phase` — only the fields the derivation reads — so the two files needn't share the whole type graph; `Phase` stays assignable, and a **new phase kind stops being assignable**, which is what preserves the compile-time exhaustiveness. This is also why the badge query embeds `game_states(phase)`: `current_turn` alone is null through bonus selection, names the wrong seat during special build, and names one seat where a parallel phase (discard, post-placement) is waiting on several.

## Type-checking

`tsconfig.json` excludes `supabase/functions` (Deno-style imports), and `supabase functions deploy` **does not type-check** — it bundles and ships. So `npm run check:edge` (`deno check`, via the pinned `deno` devDependency) is the only thing between a type error and production. It gates `npm run edge` (`check:edge && deploy`); keep that gate on any future deploy script. Nothing else enforces it — no pre-commit hook, and the one CI workflow publishes an EAS update on every push to `main` without running checks.

This matters because the game types here are a **hand-maintained mirror of `lib/catan/types.ts`**, not an import (the two files can't share a module across the Expo/Deno boundary). When a phase or `PlayerState` field changes on the client, port it here in the same change. Drift doesn't fail the build; it fails at runtime as the opaque "edge function returned non-2xx".
