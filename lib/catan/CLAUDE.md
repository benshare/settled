# Catan

Everything Catan-specific lives here. Split by what it describes:

- `board.ts` — static structure for BOTH board variants. The top-level `HEXES`/`VERTICES`/`EDGES`/`adjacentVertices` + derived adjacency are the **standard** 19-hex board; `boardFor(variant)` returns a `Board` bundle (graph + resource/number/port config + layout natural-dims) for `'standard'` or `'expanded'`. `Hex`/`Vertex`/`Edge` are opaque `string`s (not literal unions) so both boards — whose ID namespaces overlap and differ in size — share one type; per-variant validity is enforced by the check scripts, not the compiler. Variant-aware code must resolve `boardFor(state.variant)` rather than importing the top-level standard constants. Each bundle also carries `spiralNumberSequence` — the fixed high/low token order for the `'spiral'` number layout (standard = authentic Catan A-R; expanded = tuned so reds never land adjacent), same multiset as `numbers`.
- `boardExpanded.ts` — GENERATED (by `dev/gen-expanded-board.ts`) geometry for the expanded 30-hex board (rows 3-4-5-6-5-4-3): `EXPANDED_HEXES/VERTICES/EDGES/adjacentVertices/COASTAL_EDGES/PORT_SLOTS`. Do not hand-edit; regenerate and paste. Same invariants as the standard board (adjacentVertices N-clockwise, EDGES sorted, COASTAL_EDGES a clockwise ring). Mirrored in the edge function.
- `colors.ts` — pure rules for player colors: `COLOR_IDS` / `ColorId` (the six ids), `DEFAULT_COLOR_ORDER`, `COLOR_LABELS`, `parseColorPrefs`, `parseGameColors`, and `resolveColorPreferences`. No I/O. **The id order is the pre-preferences convention** — `COLOR_IDS[seat]` is the color that seat used to get by definition, which is what makes both the settings screen's opening arrangement and the `games.colors` backfill one-liners. `resolveColorPreferences(prefs, rng)` walks every seat's ranking a depth at a time, giving each free color to its sole claimant or to a random one of several, and letting a seat whose choice is already taken fall through to the next depth; whoever is still unassigned draws from what's left at random. `rng` is injectable so `dev/check-catan-colors.ts` can assert exact outcomes. **`parseColorPrefs` deliberately does not pad**: an empty `profiles.color_prefs` means _no preference_ and resolves entirely at random, NOT to the default order — padding it would silently give every player who never opened the screen the old seat-index colors. Mirrored in the edge function, which is the only place the resolve actually runs.
- `types.ts` — `GameState`, `Phase`, sparse-storage helpers (`vertexStateOf`, `edgeStateOf`), and `GameConfig` (with `parseGameConfig` / `summarizeGameConfig` / `parseExtraBuild`). All persisted shapes. **`GameConfig` is persisted on `games.config`, not on the `game_states` row** — it is immutable metadata, written once at creation, and the spectator RLS policies need to read it from the `games` row (see the Spectating section). `GameState.config` is therefore assembled in `gameContext.tsx` by joining the two rows. `GameConfig.extraBuild` (`ExtraBuildConfig`: `{ enabled, buildPhases: 'every' | 'across', moreThanSeven }`) configures the 5-6 player **special build phase**; the `special_build` Phase variant (`{ queue: number[] }`) drives it. `summarizeGameConfig` surfaces non-default extra-build settings only when `playerCount > 4`. `GameConfig.honk` (boolean, default `true`) is the per-game on/off for the Honk nudge — parsed defensively (a missing value defaults to enabled, so legacy rows keep honking), gated in `canHonk` and the edge `handleHonk`, and set by the create-game "Honking" toggle. `GameConfig.friendlyRobber` (boolean, default `false`) suppresses the robber during the first full go-around (`state.round < playerCount`): the gate lives **only** in the edge function's `applyRollOutcome` (server-authoritative — no pure-rules mirror), where a 7 in that window applies nomad desert production and returns to `main` (via `wrapMagicianWindow`) instead of entering the `discard`/`move_robber` chain — no discards, no move, no steal. Parsed defensively (missing → `false`, so legacy rows keep the standard robber) and set by the create-game "Friendly robber" toggle. `GameConfig.limitMonopoly` (boolean, default `false`, parsed defensively) caps what a single opponent loses to a Monopoly play at `monopolyCap(playerCount)` (3 at ≤4 players, 2 above); the aggregate haul stays uncapped. Enforced **only** in the edge function's `monopoly` case in `handlePlayDevCard` (server-authoritative — no pure-rules mirror), where `monopolyCap` is duplicated; the create-game "Limit monopoly" toggle sets it (hidden when dev cards are off) and `MonopolyPicker` restates the cap in its subtitle. `GameConfig.bonusCount` / `curseCount` (1-3, default 2 / 1, read through `clampCardCount` since `config` is unvalidated JSON) are how many bonus / curse cards each player chooses between in `select_bonus`; a count of 1 is dealt rather than chosen, and **both at 1 skips the phase entirely** (`needsBonusSelection`) — the cards are assigned at creation and the game opens on placement. `GameConfig.tradeMode` (`'automatic' | 'confirm'`, default/legacy `'automatic'`, parsed defensively) is the player-to-player trade acceptance mode — see `trade.ts`; set by the create-game "Trades" segmented control. `GameConfig.timeout` (`TimeoutOption | null`, default `'2d'`) is the per-move idle window — and the **one field that does not fall back to `DEFAULT_CONFIG` in `parseGameConfig`**: an unrecognized or missing value reads as `null` (no clock), because a stored row records the clock a game was actually played under and moving the default must not rewrite it. Games and pending requests in flight when the default moved were given the key by migration (`20260806120000_default_move_timeout.sql`) instead — see the Move timeouts section and `timeout.ts`; set by the create-game "Move timeout" `Select`. `GameConfig.spectators` (boolean, default `true`, parsed defensively) records whether friends of any player may watch, and **is** the authority for access: the RLS policies read it straight off `games.config`. See `.claude/specs/spectating.md`. Also holds `UNDOABLE_ACTIONS` / `UndoSnapshot` and `GameState.undo` — see the Undo section, and `GameSize` / `gameSizeFor` — see the Game size section. **`GameState.colors` (`ColorId[]`, one per seat) is persisted on `games.colors`, not on `game_states`** — for the same reason as `config`: immutable metadata written once at creation. `gameContext.tsx` joins it in through `parseGameColors`, so `BoardState` is `Omit<GameState, 'config' | 'colors'>`. See the Player colors section.
- `generate.ts` — fresh-game initialization: variant-keyed hex/port generation (reads counts/numbers/port composition from `boardFor(variant)`; the expanded board has 2 deserts, 28 tokens, and 11 ports = standard 9 + one 3:1 + one sheep 2:1), `initialGameState`, and `dealBonusHands`. `generateHexes(variant, layout)` places resources/deserts by shuffle either way; number tokens follow `config.numberLayout`: `'random'` shuffles the bag, `'spiral'` lays `board.spiralNumberSequence` along a spiral hex-walk (outer ring → center, from a random start corner + CW/CCW direction, skipping deserts) so 6s/8s spread out. The spiral geometry is derived from hex-ID row prefixes (kept identical to the edge mirror), not from `board.hexRows`. `NumberLayout` is on `GameConfig` (default `'spiral'`); the create-game "Random numbers" toggle flips it. (Resource/desert placement is always random.) (every player's `select_bonus` hand dealt in one pass — `config.bonusCount` bonuses + `config.curseCount` curses each — drawing without replacement across the whole table; a hand's own cards are always distinct even when `config.bonusSets` filters the pool below what the table wants, and when `bannedCombos` is on **every** offered bonus is compatible with **every** offered curse, so whichever pair the player keeps is legal by construction; cards withheld at the table's `GameSize` are dropped before the set filter, and `pickPool` widens the net — set ∩ available, then available, then the full pool — so a filter can narrow the deal but never break it. Cross-table uniqueness degrades only where the pool runs out: 6 players × 3 curses outnumber the 11-card curse pool, and the dealer reshuffles after a full pass, so repeats come last). Real games are dealt by the edge function's mirror of `dealBonusHands` — `initialGameState` is only reached from the `dev/` check scripts, so an edge deploy (`npm run edge`) is required for any deal-rules change to reach players.
- `placement.ts` — pure rules for the initial-placement phase (validity, target-settlement derivation, snake-order turn advance, starting-resource grant). Also the two helpers behind the **drafted turn** — `applyPlacementDraft` (the client's local simulation of a partly-chosen turn, so a later piece's valid spots are computed against the earlier ones; never persisted) and `placementPairsExpected` (2 for seat `N-1` on its round-1 turn, 1 otherwise; mirrored in the edge function, which validates the submitted count against it). Also the `pick_last` step's three helpers — `isDoublePlacementSeat` (seat `N-1`, the only one that places both settlements back-to-back), `ownSettlementVertices`, and `swapPlacementPairs` (the log rewrite, typed against `unknown[]` since its only caller is the edge function; it lives here rather than inline there so the check script can exercise it, the same arrangement `honk.ts` uses). See the initial-placement section below. No I/O; callable from UI helpers and tests.
- `roll.ts` — pure rules for the main-phase loop (dice roll, per-hex resource distribution, forward turn rotation). `gainsFromHex(state, hex, total)` is the one-hex, **robber-blind** slice the forger copies through; `distributeResourcesByHex` is that function over every hex minus the robber's, and `distributeResources` sums it. Anything that needs "what would this hex pay" regardless of the robber must go through `gainsFromHex` rather than reaching into the per-hex map, which has already dropped the blocked hex. Also `acrossSeat` + `specialBuildQueue(eb, enderIdx, n)` — the special-build order after a turn ends (`across` = `[(ender + ⌊n/2⌋) % n]`; `every` = all others clockwise from `ender+1`; `[]` when disabled or ≤4 players). No I/O; callable from UI helpers and tests.
- `build.ts` — pure rules for main-phase builds (road, settlement, city): costs, affordability, validity (including the "no road through opponent settlement" rule). Also `handSize` and `canTakeSpecialBuildAction(state, idx)` (any build or dev-card buy available now, honoring `moreThanSeven`; scouts gate the dev-card branch on `canScoutAffordDevCard`; bank/port trades are NOT special-build actions) used to auto-skip idle special-builders. **Road affordability is not a single boolean**: `payableBuildRoadEdges(state, idx)` is `validBuildRoadEdges` narrowed to what the hand can cover, which for a fencer holding only one of Wood/Brick is just their own reserved edges (`ownFenceRoadEdges`) — the road button, the board's pulse layer, and both `canTakeSpecialBuildAction` mirrors gate on that set rather than on `canAffordPurchase(p, 'road')`, or a fencer with a single card looks broke. `canAffordFenceRoad` / `fencePayChoice` are the two hand predicates behind it (≥1 of either card; both cards, i.e. the picker has something to ask). Free roads (explorer, Road Building) stay on the unnarrowed `validBuildRoadEdges`. No I/O; callable from UI helpers and tests.
- `trade.ts` — pure rules for player-to-player trade offers: shape validity, affordability, offer-addressing, hand swap, `rejectedByOf`/`acceptedByOf`. A game carries at most one open `TradeOffer` at a time. No I/O. **Trade mode** (`GameConfig.tradeMode`, `'automatic' | 'confirm'`, default/legacy `'automatic'`) governs acceptance: `'automatic'` swaps the moment an addressee accepts; `'confirm'` instead accumulates accepters in `TradeOffer.acceptedBy` (the offer stays open) and the proposer executes the swap with one of them via `confirm_trade`. Reject doubles as withdraw in confirm mode (drops the caller from `acceptedBy`). The actual swap always logs `trade_accepted` (on accept in automatic, on confirm in confirm) so ActionLog + `gameStats` are mode-agnostic; the interim acceptance logs an ephemeral `trade_accept_offered` (omitted from the log). The confirm-mode banner UI lives in `TradeBanner.tsx` (accepter chips for the proposer, a "Waiting…"/Withdraw state for an accepter), keyed purely off `acceptedBy` — empty in automatic mode, so no mode flag is threaded into the component.
- `ports.ts` — pure rules for ports (harbors) and bank trades: which port kinds a player has access to, which bank ratios they can use (2:1 specific / 3:1 generic / 4:1 default), shape validity for multi-group bank trades, hand update. No I/O. **A bank trade is not priced at one chosen ratio** — see the bank-combination section below; `bankPartitionFor` is the validity test the UI and the server both gate on, and the older per-kind helpers (`isValidBankTradeShape` / `effectiveBankRatioFor` / `ratioOf` / `lockedGiveResource`) survive here as the primitives it and the rate hint are built from. Only the combination layer is mirrored server-side.
- `robber.ts` — pure rules for the 7-roll chain: discard requirements, robber-movement validity, steal candidates. No I/O; callable from UI helpers and tests. `isForcedFullDiscard` flags a required count that equals the whole hand — a discard with exactly one valid selection, which only the `avarice` curse produces (a shepherd under avarice owes `total − sheep` and still chooses). The edge function's `applyForcedDiscards` takes those hands itself inside `applyRollOutcome`, before the phase is chosen, so the player never sees a prompt with no decision in it and a table where the cursed player was the only one over the limit skips the `discard` phase entirely. The auto-taken discard still logs an ordinary `discarded` event.
- `devCards.ts` — static dev-card data: `DevCardId` union, `DEV_CARD_POOL` (title/description/icon), `DEV_DECK_COMPOSITION` (classic 14/5/2/2/2 split). Mirror of `bonuses/`.
- `bonuses/` — static bonus + curse card data. `index.ts` defines shared types (`BonusId`, `CurseId`, `Bonus`, `Curse`) and re-exports. `bonuses.ts` has `BONUS_POOL`; `curses.ts` has `CURSE_POOL`; `combos.ts` has `BANNED_BONUSES_BY_CURSE` (+ `isBannedCombo`), the bonus/curse pairings that shouldn't be dealt together — indexed by curse, every curse listing the bonuses it excludes. `sizes.ts` is the **one location for per-player-count deviations** — see the Game size section below. All four are mirrored in the edge function.
- `bonus.ts` — pure rules for sets 1, 2, and 3. Set 1: VP threshold (`winVPThresholdFor` takes both bonus + curse), port discount (`effectiveBankRatio`), underdog multiplier (`underdogMultiplierFor`), bricklayer alt cost (`bricklayerAltCost`, `BRICKLAYER_COST`), carpenter VP (`canBuyCarpenterVP`, `carpenterVPOf`), veteran knight tap (`availableKnightsToTap`, `canTapKnight`), gambler reroll (`canReroll`), aristocrat placement (`grantsStartingResourcesOnRound`), nomad d5 (`nomadResourceForRoll`). Set 2: populist VP (`populistBonusVPFor`, `pipCountFor`, `pipsAtVertex`), shepherd hand size (`shepherdEffectiveHandSize`, `canShepherdSwap`), ritualist (`isValidRitualTotal`, `ritualCardCost`, `dicePairForTotal`, `canRitualRoll`), fortune teller chain trigger (`fortuneTellerTriggersOn`), curio collector trigger (`curioCollectorTriggers`), metropolitan (`canBuildMoreSuperCities`, `superCityCount`, `metropolitanWheatSwapDelta`, `metropolitanCityCost`), forger (`forgerTokenHex`, `mustMoveForgerToken`, `canMoveForgerToken`, `hexesAdjacentTo`), scout (`isValidScoutSwap`, `scoutDevCardCost`, `scoutSwapOptions`/`affordableScoutSwaps`/`canScoutAffordDevCard` — a scout can pay the dev-card cost with a substituted resource, so buy-detection and the client cost picker gate on the affordable swap routes, not the standard cost), accountant (`roadLiquidationBlocked`, `ROAD_REFUND`/`SETTLEMENT_REFUND`/`CITY_REFUND`/`SUPER_CITY_REFUND`/`DEV_CARD_REFUND`). Set 3: plutocrat gain (`plutocratGain` — +50% on ≥2 of a resource, applied inside `distributeResources`), merchant add-on (`isValidMerchantAddon`, `singleGiveResource`, `MerchantAddon` — the pre-combination 1:1 side-conversion, kept only to validate a legacy `bank_trade` payload server-side; the live rule is the ratio-1 rate in `bankPartitionFor`), fencer (`FENCE_TOKEN_COUNT`, `fenceOwner`, `isFenceReservedAgainst`, `fenceRoadCost` — reserved edges in `GameState.fenceTokens`), smith brick↔ore (`smithCostOf`, `isValidSmithSwap`, `smithPortResourceOk` — fungible for builds/dev/ports), investor (`canInvest`, `investorTokenCount`, `investorPayout`, `INVESTOR_MAX_TOKENS`/`INVEST_TRIO`/`INVESTOR_ACTIVATE_VP` — gated at ≥3 VP, `PlayerState.investments`), magician (`isValidMagicTarget`, `magicDiscardCount` — post-roll phantom production), haunt (`resolveHauntGhosts`, `isGhost`, `HAUNT_SPOT_COUNT` — spawns 0-VP `'ghost'` buildings on blocked secret spots in `PlayerState.hauntSpots`). Singular filename (parallel to `dev.ts`) because `bonuses/` already owns the plural name.
- `dev.ts` — pure rules for development cards: cost, deck build + shuffle, buy/play validity, Largest Army recomputation, `totalVP` (including Longest Road +2 and hidden VP cards for self-views). No I/O.
- `longestRoad.ts` — pure rules for the Longest Road bonus: `longestRoadFor` walks an edge-disjoint trail per player (opponent buildings block pass-through at interior vertices); `recomputeLongestRoad` returns the new holder (≥5 trail, strict majority; ties keep current holder). No I/O.
- `honk.ts` — pure rules for the Honk nudge (`HONK_IDLE_MS` = 1 min, `lastActivityAt`, `honkTargetFor`, `honkersThisTurn`, `canHonk`). Derived entirely from `games.events` plus the per-game `config.honk` on/off flag — no other `GameState` field, no migration. `canHonk` takes an `enabled` arg (pass `gameState.config.honk !== false`, so legacy games with no stored value stay honkable); the edge `handleHonk` rejects with `config.honk === false`. `canHonk` gates the button in `MainLoopBar` / `SpecialBuildBar` and authorizes `handleHonk` server-side, so the two can't disagree; `now` is a parameter to keep it pure. Honkable in `roll`, `main`, and `special_build` only — the sub-phases (discard, robber, bonus picks) are already blocking prompts. Three rules are load-bearing and easy to break: **`honked` events are excluded from the idle clock** (counting them would let the first honker's ping restart the window and lock everyone else out, collapsing one-honk-per-sender into one-honk-total), **the per-turn window is everything after the last `turn_ended`** (which is what makes the allowance reset for free), and **the target comes from `honkTargetFor`, not `current_turn`** — during `special_build` the stalled player is `phase.queue[0]` while `current_turn` has already advanced to the next roller. The allowance is keyed per-target, since one turn window holds every special builder plus the roller. No I/O.
- `timeout.ts` — pure rules for **move timeouts** (`TIMEOUT_OPTIONS` / `timeoutMs` / `timeoutLabel`, `TIMEOUT_PENALTY_MS`, `pendingSeats`, `deadlineFor`, `warningStageDue`, `formatRemaining`). See the Move timeouts section below. Mirrored in the edge function, which owns both writing `games.deadline_at` and acting on it. No I/O, no React — the ticking half is `useCountdown.ts`.
- `useCountdown.ts` — the one React hook that turns `games.deadline_at` into a live remaining-time number, returning `null` until the deadline is inside `COUNTDOWN_VISIBLE_MS` (an hour) so a 7-day game runs no interval and shows no number for six and a half of those days. Kept out of `timeout.ts` precisely so that file can stay a pure mirror. Mount it **once per surface, not once per seat** — `PlayerStrip` calls it for the whole strip.
- `ActionLog.tsx` — the floating log panel. Read-only formatting of `games.events` via `describeEvent`, plus a single-select filter chip row (All / Rolls / Builds / Trades / Robber / Bonuses). The chips read a local `CATEGORIES` map of event kinds, declared `satisfies Record<string, GameEvent['kind'][]>` so a renamed kind fails to compile instead of silently filtering to nothing; buckets **overlap** on purpose (a `ritual_roll` is both a roll and a bonus). `describeEvent` returns `null` for ephemeral bookkeeping (`turn_ended`, trade negotiation, `magic_skipped`), and its `default` case swallows anything unknown — so **a new event kind added to the edge function must also be added to the `GameEvent` union in `lib/stores/useGamesStore.ts`**, or it will be written server-side and never appear in anyone's log. Two events exist purely so the log explains itself: `bonus_chosen` (one per seat, written by `handlePickBonus` only once **every** player has locked in, so an early picker's bonus can't leak — or by `handleRespond` at creation for games that skip the selection phase; it carries `offered` / `offeredCurses`, the only surviving record of the cards turned down, which `game_results` reads back for pick rate) and `hoarder_kept` (a hoarder over the limit on a 7 discards nothing, which otherwise looks like the 7 skipped them). **Expandable rows**: `describeEvent` may return a `detail` array alongside the summary text, which is what makes a row tappable (chevron + expanded body); rows without it stay inert. All rows start collapsed and expansion state is local to the panel, keyed by `${at}-${index}` so a row stays open as newer events land above it. Roll expansion needs server help — production is otherwise recorded nowhere, so `applyRollOutcome` hangs a per-seat `gains` map off the `rolled`/`ritual_roll` event by mutating the caller's event object before it's persisted. `gains` is **optional**: pre-existing rolls don't have it, and `gainsDetail` returns `undefined` (not an empty list) in that case so an old row reads as un-expandable rather than claiming nobody collected. Passive bonuses with no discrete moment — plutocrat's production bump, bricklayer/smith/fencer cost substitutions, underdog/populist/thrill-seeker scoring — are deliberately unlogged: the log records actions, and it never reports per-roll production in the first place.
- `GameOverOverlay.tsx` — end-of-game modal shown when `games.status === 'complete'`, with three tabs: **Scores** (final scoreboard, reveals every player's hidden VP cards), **Rolls** (the shared 2–12 dice histogram), and **Highlights** (fun superlatives). Takes the full `events` log as a prop; the Rolls/Highlights tabs are pure derivations from it via `gameStats.ts`. Exports `FinalScoreButton` for the reopen affordance after dismiss. **Rematch** is an optional `onRematch` handler, not navigation done here — `app/game/[id].tsx` supplies it (and omits it for a spectator, who has no seat), routing to `/create-game` with the other players' ids and this game's `GameConfig` as route params. The create screen seeds its form from those instead of the profile's saved defaults; see `app/(app)/create-game.tsx`.
- `gameStats.ts` — pure, client-only recap derivations over `games.events` (NOT mirrored in the edge function; no authority over state). `rollDistribution` counts shared `rolled` totals (bonus rolls excluded); `gameHighlights` computes the eight superlatives (Friendliest/Antisocial = most/fewest accepted player-to-player trades with both parties credited; Klutziest = cards discarded to 7s; Most Targeted = robber steals suffered; Biggest Honker/Honk-ee = honks sent/received; Speediest/Slowest = lowest/highest median whole-turn duration, where a turn spans the boundary that opens it — the prior `turn_ended`, or `placement_complete` for the first turn — to its own `turn_ended`). A highlight shows all seats tied for the extreme, or no winner when everybody ties (no standout) — which also covers the all-zero case for "most" awards.
- `palette.ts` — the physical-game palette, re-exported from `catanColors` in `lib/theme.ts`, plus the two seat → hex lookups: `seatColor(state, seat)` and `seatColors(state)`. **`playerColors` is keyed by `ColorId`, not by seat index** — never index it with a seat number; go through `seatColor`, or the color a player sees will stop matching the one the game assigned them.
- `gameContext.tsx` — React context that loads the per-game `games` row + `game_states` row and subscribes to realtime. Use `useGame()` in any subtree under `<GameProvider>`. The exposed `gameState` is a **join of both rows**: the `game_states` row supplies the board (`BoardState`, a `GameState` minus `config`) and the `games` row supplies `config`, so `gameState` stays `undefined` until both have landed rather than briefly publishing a `GameState` with no config. Also exposes `isSpectator` (the viewer isn't in `game.participants`) and `watcherIds` — read both from the context rather than re-deriving, so the board and the chat can't disagree about who is watching. `watcherIds` comes from a third channel, an **ephemeral Supabase Presence** channel (`watchers:<gameId>`): everyone in the game joins it, but only spectators `track()`, so the roster is watchers rather than attendance. It owes the same realtime debts as the other two (`uniqueTopic`, torn down and rebuilt on `resyncNonce`, `track()` re-issued from the `SUBSCRIBED` callback so it survives an automatic rejoin). Presence is best-effort by construction — a dropped socket under-counts until the next foreground, which is precisely why it is presence and not a heartbeat table. Both rows are re-fetched and both channels re-subscribed on every app foreground (`useAppForeground`), because realtime events emitted while the app was backgrounded are never delivered. Both rows are also re-read whenever the viewer's own action succeeds (`lib/gameSync.ts`), so the board never depends on a channel to show the viewer a move they just made. The provider is **not** remounted when the header's tab strip switches games (same route, new param), so every piece of per-game state it holds — `liveGame`, `gameState`, `stateLoaded` — is cleared on a `gameId` change rather than relying on a fresh mount; `game` falls back to the store's row, which is already keyed to the new id, so nothing flashes. Read `lib/stores/CLAUDE.md` before touching any of this — the rules there are load-bearing.
- `chatContext.tsx` — React context for the per-game chat thread (`game_messages`) plus the read cursor (`game_chat_reads`). Use `useChat()` under `<ChatProvider>`. Owes the same realtime debt as `gameContext.tsx` (`uniqueTopic`, refetch on `SUBSCRIBED`, resync on foreground, monotonic seq) — read `lib/stores/CLAUDE.md` first. The read cursor does double duty: it backs the unread badge **and** acts as a presence heartbeat (upserted every 15s while the panel is open) that the edge function reads to suppress a push for someone already looking at the thread. `CHAT_PRESENCE_MS` is mirrored in `game-service`; the heartbeat interval is deliberately half of it so one missed beat can't read as "away". It also owns the **typing indicator**: `typingIds` + `noteTyping`, backed by a second, ephemeral Supabase Presence channel `chat_typing:<gameId>` keyed by user id — the same shape as `watchers:` in `gameContext.tsx`, and for the same reason (typing must disappear when a client vanishes; a broadcast heartbeat would leave it stuck for one interval after a crash). Three things about it are deliberate: **membership _is_ the signal** — the viewer `track()`s/`untrack()`s rather than tracking a `{ typing }` flag, so a panel open/close doesn't emit an event for a state nobody reads; **the channel is joined only while the panel is open**, since the indicator has no closed-panel surface (so two people with chat shut don't see each other type — neither has anywhere to show it), which also stops the viewer being tracked on close for free; and **`track` is asserted from the `SUBSCRIBED` callback** via a `typingRef`, not just from the transition effect, so a reconnect mid-sentence keeps showing the viewer as typing. `typing` is a boolean, so a fast typist emits one `track` per burst rather than one per keystroke, and it is forced false whenever `open` goes false. `TYPING_IDLE_MS` (4s from the last keystroke) is unrelated to `CHAT_PRESENCE_MS` — that one suppresses a push, this one drives an animation — and exists so a draft abandoned mid-sentence doesn't pin the indicator on. An emptied composer stops typing immediately rather than after the window. See `.claude/specs/chat-typing-indicator.md`.
- `GameChat.tsx` — two exports, deliberately mounted at different levels of the game screen (see `lib/game/CLAUDE.md`). `ChatButton` is the floating affordance with its unread badge, rendered by `BoardArea.tsx` in the third slot below `BoardLegend` and `ActionLog` (`top: spacing.sm + 2 * (32 + spacing.xs)`), so it sits inside the board container with them. `ChatPanel` is the conversation, mounted at the screen root (`app/game/[id].tsx`) so it covers the action bars but leaves the screen header clear — it is an absolutely-positioned view rather than a `Modal` **precisely so it stays inside the play area**; a `Modal` would cover the whole screen. ## Bank trades combine rates

A bank trade is **not** priced at one chosen ratio. The give is cut into groups
— each group a whole number of cards of one resource, at one of the rates that
resource is available at — and the number of groups is the number of cards
received. So a 2:1 wheat port and the 4:1 bank combine in one trade: 2 wheat +
4 wood buys 2 cards. `bankPartitionFor(state, idx, give, receive)` in `ports.ts`
is the whole rule, and a **non-null return is both the validity answer and the
record of what was charged** — the client gates the button on it and the server
logs the partition it returns. See `.claude/specs/trade-refactor.md`.

- **`bankRatesFor` owns which rates apply to which resource**: 4:1 always, 3:1
  with a generic port, 2:1 with that resource's specific port (or, for a smith,
  its brick/ore counterpart). Provinciality rewrites the whole map — `flat_5`
  collapses it to 5 and ignores ports, `none` empties it. The **specialist
  discount is unchanged**: it applies only when the whole give is a single stack
  of the declared resource, so a mixed give loses it exactly as it always did.
- **Reachability is a DP, not arithmetic.** A rate set has holes — {2, 4} can't
  make an odd pile, {3, 4} can't make 5 — so a min/max range check would wave
  invalid trades through. Hands are tiny; the cost is nothing.
- **The merchant's 1:1 extras are ordinary groups now.** For a single-resource
  give, the merchant gains a ratio-1 rate usable only alongside at least one
  full-price group (a card for a card is not a trade). There is no `merchant`
  payload on the action any more — the edge still folds a legacy one into
  give/receive before validating, so a client on an older bundle stays correct.
- **`ratio` on the `bank_trade` event is now optional**, written only when the
  partition was uniform; `rates` carries the breakdown either way. `ActionLog`
  renders whichever it has, and still renders the legacy `merchant` row.

## Game size (bonus / curse variants by player count)

A card may read, behave, or deal differently depending on how big the table is. `GameSize` (`types.ts`) is `'small'` (2 players) / `'standard'` (3-4) / `'expanded'` (5-6), derived by `gameSizeFor(playerCount)` and **never persisted** — deliberately separate from `Variant`, since a card can vary at 2 players where the board does not.

- **`bonuses/sizes.ts` is the one location for the deviations.** `BONUS_SIZE_VARIANTS` / `CURSE_SIZE_VARIANTS` are keyed card id → size → `{ description?, available?, …params }`. `BONUS_POOL` / `CURSE_POOL` stay the `standard` baseline and the fallback for every size with no entry, so a card that doesn't vary needs no entry at all — **31 of the 38 cards have no entry**. The 7 that do: age (card limit 5/6/7), provinciality (surcharge / 5:1 / no bank at all), gambler (reroll vs roll-twice-keep-either), ritualist (flat 3 / city-dependent / flat 2), fortune_teller (double gains at 5-6), investor (not dealt at 2, no VP gate at 5-6), magician (2-player cooldown, cheaper casts at 5-6). Full table in `.claude/specs/bonus-size-variants.md`.
- **Retuning a card is exactly two edits**: its entry in `sizes.ts`, and a `switch (size)` (or a `bonusVariantFor(id, size)?.param` read) in that card's rule helper in `bonus.ts` / `curses.ts`. Helpers that already take `GameState` derive the size themselves; the ones taking only a card id gain an explicit `size` parameter as they're retuned — signatures change per card, so each card's diff stays self-contained.
- **Params are typed per card** (`BonusSizeParams` / `CurseSizeParams`), so a param declared on the wrong card fails to compile instead of reading back `undefined`. Numbers live next to the sentence describing them precisely so the two can't drift.
- **Never read `.description` off a pool entry where a player count is known** — use `bonusDescriptionFor(id, size)` / `curseDescriptionFor(id, size)`. In-game callers get the count from `playerOrder.length` / `gameState.players.length`; the stats Catalog tab has no game, so it renders a size selector (defaulting to `standard`) and dims cards unavailable at the selected size.
- **`available: false` gates the DEAL only.** A card someone already holds still resolves a description at every size, so a game in flight — or one dealt before a card was withheld — can never render blank. Only `investor` at `small` uses it today.
- **A variant that isn't just a number needs its own machinery, and three have it.** Provinciality's small version is priced into the ratio (`bankSurchargeFor`, `ports.ts`) rather than the `BankKind` list, because a surcharged 2:1 port has no `BankKind` to name it; its expanded version empties `availableBankOptions`, and an empty list is the signal the UI reads to disable the bank button. The gambler's expanded version puts a second pair in `phase.pending.altDice` and has `confirm_roll` carry a `which` (plus a `roll_choice` event, so the choice shows up in the log the way a reroll does). The magician's 2-player cooldown is the one rule here that needed **new player state** — `PlayerState.lastMagicRound`, stamped on cast and never on skip; since `round` counts turns rather than go-arounds, a seat's own turns are `playerCount` apart and the gate is `round > lastMagicRound + playerCount`. It is enforced by `wrapMagicianWindow` declining to open, never by rejecting a cast, so nobody is shown a sheet they cannot act on.

## Undo (one step)

A player may take back their own last action when it was **solo and information-free** — `UNDOABLE_ACTIONS` in `types.ts` (builds, bank/port trades, liquidate, invest, carpenter VP, knight tap, fence token, explorer road), mirrored in the edge function, which is the authority. Rolling, buying or playing a dev card, and every trade involving another player are excluded on principle: taking those actions reveals something, so unwinding them would leak it.

Three things about the mechanism are load-bearing:

- **It restores a snapshot, it does not compute an inverse.** The edge function's dispatcher reads the `game_states` row before an undoable action and stashes it on `game_states.undo` (a jsonb column) once the handler succeeds; `handleUndo` writes it back. A single road build can move Longest Road, consume a fence token, apply a smith or bricklayer cost substitution, and bump the age curse's spend counter — an inverse would have to track every bonus we add, and would silently rot the first time one didn't.
- **The snapshot is maintained in `serve`, not in the handlers.** An action opts into undo by joining `UNDOABLE_ACTIONS` and doing nothing else. Every other action clears the column on success (guarded on `undo is not null`, so the usual case matches no rows and emits no realtime event); `send_message` is the sole exemption, because chat writes neither `game_states` nor `games.events`. `honk` deliberately is _not_ exempt — it appends to `games.events`, which undo truncates by length.
- **Undo truncates `games.events` back to its pre-action length**, so the undone action vanishes from `ActionLog` rather than being annotated. Nothing is logged in its place.

`GameState.undo` is what the client reads to decide whether to show the arrow — never a derivation from the event log. Only the acting seat may undo, and a game-winning action can't be undone at all (`games.status` is already `complete` and `game_results` is written; the orphan snapshot such a build leaves behind is inert). The arrow follows whoever holds the floor, which during `special_build` is `phase.queue[0]` rather than `current_turn` — see `lib/game/CLAUDE.md`. Full design in `.claude/specs/undo.md`.

## Forfeiting and ending

Two withdrawable, per-player declarations that a game can end without anyone reaching the VP threshold. Both are plain user-id arrays on the **games** row (`forfeits`, `end_votes`) — game metadata, like `config`, not board state — written only by the edge function's `set_forfeit` / `set_end_vote`. Full design in `.claude/specs/forfeit-and-end-game.md`.

- **Forfeit.** When every seat but one holds a standing forfeit, the game ends: `status = 'complete'`, the survivor is `winner`, and the terminal `game_complete` event carries `by_forfeit: true`. The survivor wins **regardless of VP** — `findWinner` is not consulted.
- **End game.** Needs the whole table. When the last seat votes, `status = 'canceled'`, `winner` stays null, and a `game_canceled` event is written — deliberately **not** a `game_complete`, since there is no winner and no scoreboard to announce.

The rule that keeps this small: **neither declaration has any mechanical effect while it stands.** A player who has forfeited keeps their seat, their turn, their resources and every action they could take before; nothing in the turn engine, robber chain, trade rules, discard requirements, special build queue or scoring reads either array. Only the two thresholds do. Skipping a forfeiter in turn order instead would put a new condition into every turn-advance, steal-target, trade-addressee and discard path — and withdrawing would have to splice a seat back into a queue that had moved on.

Three consequences worth knowing:

- **`isFinished(status)` (`lib/stores/useGamesStore.ts`) is the status test, not `=== 'complete'`.** A canceled game shares History, the end-of-game overlay and the "board accepts nothing" posture with a completed one. An equality check silently leaves canceled games playable.
- **An all-`N`-forfeited state is unreachable.** The `(N-1)`th forfeit ends the game, so "the winner" is always well defined.
- **Stats treat the two endings differently.** A canceled game writes no `game_results` rows at all; a forfeited one writes them with `forfeit: true` and counts toward games played and win rate only. See `lib/stats.ts`.

`GameOverOverlay` takes both as optional props: `canceled` swaps the heading for **Game canceled** and drops the winner treatment (the score/roll/highlight tabs still render — the scores as they stood are worth reading, and Rematch is still offered), while `wonByForfeit` adds a muted note under the winner. `PlayerStrip` takes `forfeitedIds` and flags those seats beside the name — a flag rather than a dimmed card, because the seat is still playing. The affordance itself is `lib/game/GameMenu.tsx`, in the nav.

## Move timeouts

A per-game clock (`GameConfig.timeout`, default `'2d'`; `null` = off) that skips
whoever is holding the game up. Rules in `timeout.ts`, enforcement entirely in
the edge function. Full design in `.claude/specs/move-timeouts.md`.

- **The clock is the game's, not a player's.** `games.deadline_at` is stamped
  after every action by anyone, so a table that is visibly playing never times
  out — the same idle model as the Honk nudge, and honks and chat messages are
  excluded from it for the same reason (a nudge is a complaint about the stall,
  not an escape from it).
- **`pendingSeats(phase, currentTurn)` is who the clock is on**, and the one
  derivation behind warning, skipping, and the countdown chip. Never
  `current_turn`: it names the wrong seat during `special_build` and is null for
  the whole simultaneous bonus-selection phase, and the parallel phases
  (`select_bonus`, `post_placement`, `discard`, `curio_pick`) are waiting on
  several seats at once. It is an exhaustive `switch`, so a new phase fails to
  compile rather than quietly becoming un-timeout-able.
- **Two players: running out of time is losing.** The seat joins
  `games.forfeits` and the game completes for the other player through the
  ordinary forfeit path — so it counts toward games played and win rate exactly
  like a manual forfeit, with no new stats shape. Both seats idle in a
  simultaneous phase cancels the game instead: nobody was there to win.
- **Three or more: the seat is skipped, and the skip is a real action.** The
  sweep picks an arbitrary legal choice and calls the ordinary handler via
  `dispatch`, so no game rule is re-implemented and `ActionLog` shows a normal
  roll / discard / end turn. There are no timeout event kinds.
- **A skipped seat's next window is one minute** (`TIMEOUT_PENALTY_MS`), until
  it acts again — `games.timed_out` holds those user ids. Otherwise an absent
  player would stall the table for a fresh full window on every go-around. Such
  a seat gets no warning push; there is no room for a ten-minute warning inside
  a one-minute window.

## Admin testing: forced rolls

A seat whose `game_states.players[i]` object carries `"dev": true` — set by hand
in the row, never written by the app — gets a picker (`DevRollPicker.tsx`) next
to the Roll button that pins their next roll to a chosen total (2–12, or
Random). The pinned total is client-side local state on the game screen
(`devRollTotal` in `gameScreenContext.tsx`) and sticky across turns, since
testing a chain usually means rolling it repeatedly.

The flag is the **authorization**, not just the affordance: `handleRoll` accepts
a `total` on the body only when the acting seat's row has `dev === true`, and
silently ignores it otherwise, so a forged request can't force a roll. The
forced dice go through `dicePairForTotal` and then the ordinary
`applyRollOutcome`, so distribution, the 7-chain, and the gambler pending path
all behave exactly as they would for a real roll. Reroll and `confirm_roll` are
untouched — a dev gambler's reroll is random.

## Player colors

Which color a player gets is **data on the game**, not a derivation from seat
order. `games.colors` holds one `ColorId` per seat, resolved once at creation
from every participant's ranking. Rules in `colors.ts`; the resolve runs only in
the edge function's `handleRespond`. See `.claude/specs/color-preferences.md`.

- **Never index the palette by seat.** `catanColors.players` /
  `playerColors` are keyed by `ColorId`. Use `seatColor(state, i)` where you
  hold a `GameState`, and take a `seatColors: readonly string[]` prop where you
  don't. Consumers split three ways, and the split is the point: components
  holding state resolve it themselves; the leaf SVG pieces (`VertexPiece`,
  `EdgePiece`, `FenceTokenPiece`) take a `color: string` and know nothing about
  seats; and the presentational ones (`ActionLog`, `GameChat`, `BuildTradeBar`,
  `TradeBanner`, `ForgerPickOverlay`, `BonusSelection`) are prop-drilled from
  `useGame().seatColors` — the same path `publicVP` / `selfVP` already take, and
  for the same reason: one derivation, so the board and the log can't disagree.
- **An empty ranking means random, not default.** `profiles.color_prefs`
  defaults to `[]`, which is every profile until they open the settings screen,
  and `resolveColorPreferences` answers that with a random color. This is a real
  behavior change from the old seat-index convention, and `parseColorPrefs`
  refusing to pad is what enforces it. The settings screen shows no rank numbers
  in that state precisely so it doesn't imply a preference that isn't stored.
- **Preferences are read at game start, not at invite time.** A
  `game_requests` row can sit pending for days; `handleRespond` reads
  `color_prefs` when the last invitee accepts. A failed profile read is not
  fatal — every seat falls back to "no preference" rather than blocking the
  game.
- **Games created before this shipped were backfilled** with
  `COLOR_IDS[seat]`, so nothing visibly changed for them. `parseGameColors`
  applies the same fallback client-side for any row that is missing, short, or
  malformed, so a seat can never render colorless and two seats can never share.

## Constants are duplicated in the edge function

`supabase/functions/game-service/index.ts` re-declares `HEXES`, `VERTICES`, `EDGES`, `adjacentVertices`, the derived adjacency, **and the full expanded board + `BOARDS`/`boardFor`/`variantForPlayerCount` from `board.ts` + `boardExpanded.ts`** (server-side copy omits layout/coastal data it doesn't need), plus the placement rules from `placement.ts` (including `isDoublePlacementSeat` / `ownSettlementVertices` / `swapPlacementPairs` for the `pick_last` step, and `placementPairsExpected` for `place_start`'s count check), the hex-generation rules from `generate.ts` (including the spiral hex-walk + `*_SPIRAL_SEQUENCE` constants + `board.spiralNumberSequence`; `handleRespond` reads `config.numberLayout ?? 'spiral'`), the roll/distribution rules from `roll.ts`, the build rules from `build.ts`, the trade rules from `trade.ts` (including the `config.tradeMode` branch in `handleAcceptTrade`, `handleConfirmTrade` for the `confirm_trade` action, and the withdraw path in `handleRejectTrade`), the robber rules from `robber.ts`, the port/bank-trade rules from `ports.ts` (including `PORT_SLOTS` + `STANDARD_PORT_KINDS`, and `bankRatesFor` / `bankPartitionFor` / `uniformRatioOf` — **the combination layer only**: the per-kind helpers the client keeps for its rate hint and check script have no server-side caller, so they are deliberately not mirrored), the dev-card rules from `dev.ts` + `devCards.ts` (deck composition, `DEV_CARD_COST`, `buildInitialDevDeck`, Largest Army recomputation), the Longest Road walk + recompute from `longestRoad.ts`, the honk rules from `honk.ts` (`HONK_IDLE_MS`, `lastActivityAt`, `honkersThisTurn`, `honkTargetFor` — inlined in `handleHonk` against loosely-typed `unknown[]` events, plus the `config.honk === false` gate mirroring `canHonk`'s `enabled` arg), the `UNDOABLE_ACTIONS` list from `types.ts` (see the Undo section — the edge copy is the authority), the color rules from `colors.ts` (`COLOR_IDS`, `parseColorPrefs`, `resolveColorPreferences`, plus `resolveColorsForPlayers` which has no client counterpart — it is the profile read; the client keeps `parseGameColors` and the injectable `rng`, which have no server-side caller), `gameSizeFor` + the two size-variant tables from `bonuses/sizes.ts` (**availability flags only** — the server holds no card copy, so the description resolvers are deliberately not mirrored; carry a param over only when a server-side rule reads it), and `totalVP` / `findWinner` (victory at 10 VP). The Deno bundler can't reliably import up-tree from `supabase/functions/`, so we accept a single redundancy: change both when rules or board data change. The source of truth is `lib/catan/`; the edge function is the copy. **The board variant is derived from player count** (`variantForPlayerCount`: 5-6 players → `'expanded'`, else `'standard'`) at game creation and persisted to `game_states.variant`; the client caps games at 6 players (`MAX_PLAYERS`).

Phase sub-phases (`discard`, `move_robber`, `steal`, `road_building`) carry a `resume: ResumePhase` pointer so effects triggered from different contexts return correctly: 7-roll chain resumes to `main`, knight played before rolling resumes to `roll`, road_building resumes to whichever phase the player was in.

**`games.current_turn` is `null` for the whole `select_bonus` phase.** Picks are parallel, so no seat holds the turn; `handleRespond` inserts the row with `current_turn: needsBonusSelection(config) ? null : 0` — bonuses being on is no longer enough, since a 1-bonus/1-curse game skips the phase and starts at seat 0 with its cards already assigned (and its `bonus_chosen` events written straight into the insert) — and `handlePickBonus` sets it to `0` in the same games update that logs the `bonus_chosen` events — i.e. exactly when the phase advances to `initial_placement`. Anything reading the column must tolerate `null` (`currentPlayerIndex` already returns `null`, and the client's `isCurrentPlayer` checks it explicitly). Games already sitting in bonus selection when this shipped keep their stale `0` until everyone picks.

**A placement turn is chosen locally and submitted whole.** `place_start` is the only way to place: one settlement+road pair — or two for seat `N-1`, whose back-to-back turns are one submission of all four pieces — validating each pair against the previous one applied (`placeSettlementPiece` / `placeRoadPiece`, which the timeout sweep's `autoActionFor` also uses to build a legal whole turn). Three consequences: **`phase.step` never names which piece is being placed** — it is `'settlement'` for the whole turn, and the stage is local state on the actor's device (`placementStage` in `lib/game/gameScreenContext.tsx`); taking a piece back is free because nothing has been sent (the placement bar's arrow is local, **not** the server's undo — placement is not in `UNDOABLE_ACTIONS`); and other clients see the settlement and its road appear together. The events are unchanged, including their per-pair `round` stamp — `pick_last` reads it. See `.claude/specs/combined-placement-step.md`.

**pick_last** is a third `initial_placement` step, and the one place the snake order pauses mid-round. Round 1 runs `0 … N-1` and round 2 runs `N-1 … 0`, so **seat `N-1` places both of its starting settlements back-to-back** with no intervening turn — nothing fixes which of the two it placed "first". After its round-2 road it therefore lands on `{ round: 2, step: 'pick_last' }` with `current_turn` held on it, and nominates one settlement via `choose_last_settlement`; **that** one pays the starting resources, which `placeSettlementPiece` defers for exactly this seat (`deferGrant`). The nomination also rewrites the log: `swapPlacementPairs` exchanges the `vertex`/`edge` payloads of the seat's two (settlement, road) pairs when it picks the round-1 one, leaving `round`/`at` on the slots so timestamps stay monotonic and each road stays with its own settlement. **Skipped entirely for an aristocrat**, who collects on both settlements and has nothing to choose — that seat keeps the old flow, grants and all. Nomad's desert `d5`s ride the grant, so they move with it. The end-of-placement transition is untouched: it still fires on seat 0's round-2 road. UI is the ordinary placement board interaction (`PlacementLayer`'s `pick_last` branch rings the two settlements; the bottom bar's confirm is pre-seeded with the round-2 one so an untouched confirm reproduces the standard rule). See `.claude/specs/last-settlement-choice.md`.

**post_placement** sits between `initial_placement` and `roll`, for any start-of-game bonus that needs a player decision. It can carry `pending.specialist` (set-1 specialist), `pending.explorer` (set-2 explorer's 3 free roads), `pending.fencer` (set-3 fencer's 2 reserved-edge tokens), and `pending.haunt` (set-3 haunt's two secret spots). All drain in parallel — once every entry resolves, the phase advances to `roll`. Players without a start-of-game bonus don't block — the phase is skipped entirely when no pending entries exist. The edge function's `postPlacementPhaseFrom` helper rebuilds the pending after any one draining so a bonus resolving never wipes another's entries.

**Gambler roll confirmation**: for gambler players the `roll` phase carries `pending.dice` after the first roll. The player either commits (via `confirm_roll`, applying distribution / 7-chain) or rerolls once (via `reroll_dice`, setting `rerolledThisTurn`). Non-gambler rolls skip the pending state and apply atomically. Reset `rerolledThisTurn`, `boughtCarpenterVPThisTurn`, `ritualWasUsedThisTurn`, `shepherdUsedThisTurn`, `forgerMovedThisTurn` on `end_turn`.

**Set-2 sub-phases** chain via recursive `resume: Phase`:

- `scout_pick` — scout dev-card buy peek (top 2); buyer picks one, the rest go to bottom of deck in drawn order. Resolved by `confirm_scout_card`. **Not entered on the deck's last card** (`state.devDeck.length > 1` gates the branch in `handleBuyDevCard`): a one-card peek is a prompt with no decision in it, so the scout falls through to the ordinary buy path and simply receives it — no `scout_buy`/peek event, and any cost swap goes unlogged the way bricklayer and smith substitutions already do. Same principle as `isForcedFullDiscard` in `robber.ts`.
- `curio_pick` — for any curio_collector who gained ≥1 card from a 2/12 original roll. Each pending entry independently claims +3 resources via `claim_curio`.
- `forger_pick` — head-of-queue forger picks one candidate to copy from for the token's hex on this roll, via `pick_forger_target`. Only entered when there are ≥2 eligible candidates; a single one is copied automatically during distribution (logged as the same `forger_copy` event). Candidates come from `gainsFromHex`, **not** the roll's per-hex map: the forger copies through the robber, so a token hex the robber is blocking still pays them what a neighbour _would_ have collected.

A roll that triggers both curio AND forger chains as `forger_pick(resume = curio_pick(resume = main))`. Bonus rolls (fortune_teller) never trigger these or the robber.

**The forger token moves only when its forger moves it.** It is seeded onto the robber's starting hex (the desert) by `handlePickBonus` when bonuses lock in, and from then on nothing else on the board relocates it — a 7 does not snap it to the robber, and `handleMoveRobber` knows nothing about it. The move is **compulsory and gates the roll**: `mustMoveForgerToken` stays true for the whole of a forger's `roll` phase until they act, `handleRoll` rejects while it is, and the client disables Roll for the same reason. A forger dealt before the seeding existed has no `forgerToken`; every reader resolves it through `forgerTokenHex(p, state.robber)`, so a legacy token materialises on the robber's current hex rather than leaving that seat unable to roll.

**Set-3 sub-phase** — `magician_pick`: opens after the _magician's own_ roll fully resolves (distribution + any 7-chain). Wraps outermost (before curio/forger reactions) so the magician acts first — its phantom production doesn't affect their inputs. The magician either `cast_magic` (discard N+1 cards to also collect production as if a number N away had rolled — for themselves only, via `distributeResources(state, target)[roller]`) or `skip_magic`, then resumes. On a 7-chain the wrap is applied at the `move_robber`/`steal` → main transitions via `wrapMagicianWindow`; magician and fortune_teller are mutually exclusive by roller bonus. UI: see the two overlay rules below.

## Two rules for sub-phase overlays

Both exist so the board — the thing the whole screen is about — stays reachable. Break either and a player ends up staring at a sheet they can't get past.

1. **Only the acting player gets a modal.** Everyone else gets a plain top status line in `lib/game/TopArea.tsx` (`styles.statusWrap` / `styles.statusLine`) — never an overlay. A player who is only waiting has no decision to make, so covering their board buys nothing. `magician_pick`, `scout_pick`, `curio_pick`, and `post_placement`'s specialist all follow this; `forger_pick` renders nothing at all for non-actors. There is deliberately no `*WaitOverlay` component left in this directory — if you find yourself writing one, write a status line instead.
2. **A modal whose choice depends on the board must be minimizable** — use `MinimizableModal` (see `lib/modules/CLAUDE.md`) rather than `Modal`. `MagicianPickOverlay` (which number to fake), `SpecialistDeclareOverlay`, `ForgerPickOverlay` (names a hex ID), and `AccountantPicker` (rows labeled with raw edge/vertex IDs) all qualify. `ScoutPickOverlay` is minimizable too — the sheet names the two dev cards but not whether a Knight or a Road Building is worth more on the board as it stands. Board-independent picks — resources, port ratios (`CurioPickOverlay`, `MonopolyPicker`, `YearOfPlentyPicker`, `InvestPicker`, and friends) — carry everything the player needs inside the sheet, so a plain centered `Modal` is correct there. The forger's own token move is the counter-example that proves the rule: it is not a modal at all. `ForgerMoveLayer` pulses the legal hexes on the board (the same `PulsingDot` + transparent tap circle as `RobberLayer`) and a tap goes to the shared `ConfirmBar` — a choice that is _entirely_ about board position, and compulsory, has no business behind a sheet.

**Set-3 non-phase mechanics** — plutocrat/smith/merchant/fencer/investor are inline: plutocrat bumps summed roll gain in `distributeResources` — but note the edge function's real roll path does **not** call that function: `applyRollOutcome` sums `distributeResourcesByHex` (the per-hex breakdown, which stays on base gains — the forger reads `gainsFromHex` instead, so it also sees through the robber) and applies `plutocratGain` itself right after the summation, before the gains are hung off the roll event or added to hands. Any new server-side production path has to do one or the other; summing per-hex without the bump is how plutocrat silently stopped applying. Smith swaps the brick/ore cost component (`smith_swap` on build/buy actions, and `bankRatesFor` gives them their counterpart resource's 2:1 port rate); merchant is a ratio-1 rate inside `bankPartitionFor` rather than a payload on the action — see the bank-combination section; fencer reserves edges in `GameState.fenceTokens` (new `fence_tokens` jsonb column — see migration) and pays 1 card on its own reserved edge (`fence_pay` — the server falls back to the other card when the requested one isn't in hand, so an omitted/stale choice can't dead-end a build that is affordable). Which card is the player's to choose: `FenceCostPicker` opens instead of the confirm bar when a fencer taps their own reserved edge holding **both** Wood and Brick (the metropolitan-picker pattern — the modal's button commits the build); with only one of the two there's nothing to ask and the normal confirm bar runs. Road Building's free placements never open it; investor sets aside trios into `PlayerState.investments` (`invest` action) and is paid out once its roll resolves (`applyInvestorPayout`, called from `applyRollOutcome` and — on a 7 with owed discards — from `handleDiscard`, riding the same deferral as nomad production so the payout never counts towards the 7-card discard). The `'ghost'` VertexBuilding (haunt) is worth 0 VP, produces 1, is a steal target, and is transparent to the distance rule + longest-road + road-building for others (`isGhost` guards those checks); `settlementCountFor` excludes it, `totalVP` scores it 0. A haunt player's _unspawned_ spots are drawn on the board too, but **only for that seat** — `BoardView` takes a `viewerIdx` (the seat watching, `-1` for a spectator) purely so it can render information nobody else may see, and reads `hauntSpots` off that seat alone. The marker (`HauntSpotMarker`) is an empty, player-coloured dashed outline, deliberately fainter than the filled, dark-outlined ghost it may become, so a reservation never reads as a piece already on the board; the post_placement multi-select preview uses the same marker, so committing a pick doesn't change how it looks.

**special_build** (5-6 player games, `config.extraBuild`) sits between a player's `end_turn` and the next `roll`. `handleEndTurn` advances `current_turn` and bumps `round` as usual but, instead of `roll`, writes `{ kind: 'special_build', queue }` when the queue is non-empty — `specialBuildQueue(eb, ender, N)` filtered through `drainSpecialBuildQueue` (drops leading players who `!canTakeSpecialBuildAction`). `queue[0]` is the acting builder (NOT `current_turn`); they may build road/settlement/city or buy a dev card — nothing else. **Trading of any kind (player, bank, port) is main-turn only.** Bank trades used to be allowed here and caused a lockout: trading down mid-slot dropped the builder back under the `moreThanSeven` threshold, which `isSpecialBuildActor` re-checks on every action, silently disabling the build they entered the slot for. `end_special_build` (`handleEndSpecialBuild`) pops the head, re-drains, and either continues with the next builder or falls through to `roll` for the already-advanced `current_turn`. The acting builder is gated by `isSpecialBuildActor` (queue head + `moreThanSeven` hand check); the three build/buy handlers accept it in addition to `main` (`preflightBuild(…, allowSpecialBuild=true)` for settlement/city; inline branches in `handleBuildRoad` / `handleBuyDevCard`). Super-city, carpenter-VP, tap-knight, liquidate, dev-card play, robber, roll, `handleBankTrade`, and player-trade stay `main` + `current_turn` only. Age-curse `cardsSpentThisTurn` accumulated during a builder's SBP slot is NOT reset when the slot ends — it carries forward and counts toward the card limit of the builder's own following turn (the counter is cleared only on their `end_turn`). A `scout` may buy during the SBP: `scout_pick.resume` widens to hold a `{ kind: 'special_build'; queue }` snapshot, so the peek returns the buyer to the same slot (the queue is untouched — only `end_special_build` pops it). Eligibility for a scout is `canScoutAffordDevCard`, not the standard cost, in both `canTakeSpecialBuildAction` and its server mirror — otherwise a scout who can only pay via a swap gets drained out of the queue. Notifications reuse `your_turn`. Legacy games with no `config.extraBuild` default to disabled (never disrupted). Fully mirrored in the edge function.

Note the two set-3 build interactions must both honour the special build phase: `handleBuildRoad`'s fencer-reserved-edge discount and smith `smith_swap` (and `handleBuyDevCard`/`handleBankTrade`'s smith/merchant paths) already run inside the same handlers the SBP reuses, so they work in either phase.

**placedTurn** (required field on occupied vertices and edges) records `state.round` at placement time. Initial-placement pieces stamp `placedTurn = 0`. Used by the accountant's liquidation gate (`placedTurn < state.round`) to enforce "not the same turn it was bought".

`dev/check-catan-board.ts` validates BOTH variants (counts, adjacency, coastal ring, port spacing, resource/number/port composition); `dev/gen-expanded-board.ts` regenerates the expanded geometry for `boardExpanded.ts` (run it, paste output into `boardExpanded.ts` and the edge-function mirror). When in doubt, run the check scripts — `npx tsx dev/check-catan-board.ts`, `check-catan-placement.ts`, `check-catan-roll.ts`, `check-catan-build.ts`, `check-catan-trade.ts`, `check-catan-robber.ts`, `check-catan-ports.ts`, `check-catan-dev.ts`, `check-catan-longest-road.ts`, `check-catan-curses.ts`, `check-catan-bonuses.ts`, `check-catan-honk.ts`, `check-catan-timeout.ts`, `check-catan-colors.ts` — after edits. The edge function is only validated at deploy time (`npm run edge`).

## Spectating

A game whose `games.config->>'spectators'` is true is readable by anyone who is friends with at least one of its players (three additive RLS policies on `games` / `game_states` / `game_messages`). See `.claude/specs/spectating.md` for the full design; the parts that matter in this directory:

- **`isSpectator` comes from `useGame()`, never from a local `participants.includes` check.** One derivation, so the board and the chat can't disagree.
- **The spectator view is the same components with props gated, not a forked tree.** `meIdx` is `-1` for a spectator, which already makes every seat-keyed overlay, picker, and board interaction (`interaction` / `build` / `robber` on `BoardView`) inert — the explicit `!isSpectator` gates on the bottom bars, `PlacementHeader`, `TradeBanner`, and `BonusSelection` are there to make the intent legible and to catch anything that would otherwise render an empty seat's hand. Forking the tree would guarantee drift.
- **A spectator gets no bottom bars at all**, which is where players read what the table is waiting on — so `spectatorStatus()` in `lib/game/TopArea.tsx` has to name the actor for _every_ phase, sub-phases included. A phase it doesn't cover reads as the game having silently stopped. It is an exhaustive `switch` over `Phase['kind']` on purpose: a new phase fails to compile rather than falling through to nothing.
- **Chat is two-way.** Spectators read and send; `handleSendMessage` authorizes them via `isGameSpectator`, a service-role mirror of the RLS predicate (the admin client bypasses RLS, so that function _is_ the whole authorization — keep the two in step). A spectator's message pushes the players; spectators themselves are never notification targets. The `watching` tag on a message is derived, not stored: `playerOrder.indexOf(sender) < 0`.
- **Hidden information is unchanged, not solved.** `game_states.players` holds every hand in one row and participants could always read all of it; a spectator inherits exactly that posture. Hand privacy is a client rendering convention here, not a storage boundary.
- **"May watch" ≠ "is watching".** `spectatableGames` (the store) is every game the RLS policy lets you read — a first-contact surface. The header tab strip shows only games you're _actively_ spectating: `profiles.spectating`, a per-user id array written when `GameProvider` first sees `isSpectator` (start) and cleared by `StopWatchingButton` / a game ending (stop). `useSwitchableGames` intersects the two. See `.claude/specs/spectating.md` §6b.

## Sparse storage

`GameState.vertices` and `GameState.edges` are `Partial<Record<…, …>>`. Missing keys default to `{ occupied: false }` via `vertexStateOf` / `edgeStateOf`. Code that writes state should continue to set only occupied entries — never pre-fill 54 + 72 empty entries.
